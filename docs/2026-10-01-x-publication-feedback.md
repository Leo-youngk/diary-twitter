# X 发布结果与反馈修复

## 查实的问题

- 首次同步回来的 `xposts` 行可能已经是 `sent`。旧监听因为没有上一状态而忽略它，导致成功通知缺失。
- 旧监听只处理成功，失败没有通知；手机信息流仅有一个带 hover 标题的 X 图标，具体原因不易发现。
- 两个追加入口都没有正常保存后的确认。开启 X 但超出长度限制时，新帖仍只显示「已发布」，没有说明未同步。
- 后端在整个投递批次结束后才回传状态；后续请求等待或异常会遮住前面已经取得的结果。
- FxTwitter 统计请求没有超时，与发帖共用 Durable Object 的 alarm，可能拖住后续投递与发布状态核对。

## 修复行为

- 按完整行监听首次或后续成功、失败结果。载入时已有的历史结果不弹窗；元数据更新不重复提示。
- 新帖与两个追加入口共用保存反馈，区分日记本保存、等待连接、正在同步、关闭 X 和超长未同步。写入异常时保留输入内容。
- 未完成的 X 状态和失败原因留在信息流、详情及追加下方；失败可以直接重试。已有 Buffer ID 仍沿用先查询后重试的去重规则。
- 通知放到 body 上层，位置随可视视口变化，错误保留 8 秒。
- 收到任务、开始请求以及每条结果取得时立即回传状态；后续条目异常也不能隐藏之前的结果。
- 统计请求 8 秒超时，每轮限制刷新时长；一分钟内需要继续投递时优先处理 X，推迟统计刷新。

## 验证与限制

- 在修改前，首次结果通知与失败通知的回归用例失败；修改后通过。
- Vitest 15 个文件、82 项测试通过；类型检查、lint 和生产构建通过。
- 新增覆盖首次终态、失败原因、追加元数据、旧结果抑制、离线等待、超长未同步、父帖删除、写入异常、批次逐条回传和统计请求超时。
- 本环境的完整 Vite + Workers 开发服务器受系统网络接口限制；独立前端验证服务器可启动，但云浏览器无法访问其回环地址。因此未完成浏览器视觉验证或 iPhone 真机验证。
- 只读检查正式站静态资源，确认当前运行 `2a8f4c8 · 9/30 15:19`。安全浏览器登录未完成，没有读取用户本次帖子的生产投递记录，也未发布真实测试推文。不能把以上代码缺陷直接认定为用户本次未同步的唯一原因。
- GitHub 的现有 Cloudflare 自动构建标识为 `diary-twitter`，正式站和 Wrangler 目标为 `diary-app`；提交后的构建结果和正式站资源需要分别核实。
