# X 发布结果与反馈修复

## 查实的问题

- 首次同步回来的 `xposts` 行可能已经是 `sent`。旧监听因为没有上一状态而忽略它，导致成功通知缺失。
- 旧监听只处理成功，失败没有通知；手机信息流仅有一个带 hover 标题的 X 图标，具体原因不易发现。
- 两个追加入口都没有正常保存后的确认。开启 X 但超出长度限制时，新帖仍只显示「已发布」，没有说明未同步。
- 后端在整个投递批次结束后才回传状态；后续请求等待或异常会遮住前面已经取得的结果。
- FxTwitter 统计请求没有超时，与发帖共用 Durable Object 的 alarm，可能拖住后续投递与发布状态核对。

## 修复行为

- 按完整行监听首次或后续成功、失败结果。载入时已有的历史结果不弹窗；元数据更新不重复提示。
- 新帖与两个追加入口共用保存反馈，区分日记本保存、等待连接、正在同步、关闭 X 和超长未同步。写入异常时保留输入内容。
- 未完成的 X 状态和失败原因留在信息流、详情及追加下方；失败可以直接重试。已有 Buffer ID 仍沿用先查询后重试的去重规则。
- 通知放到 body 上层，位置随可视视口变化，错误保留 8 秒。
- 收到任务、开始请求以及每条结果取得时立即回传状态；后续条目异常也不能隐藏之前的结果。
- 统计请求 8 秒超时，每轮限制刷新时长；一分钟内需要继续投递时优先处理 X，推迟统计刷新。

## 生产故障与任务循环修复（10 月 2 日）

- 生产日志明确返回 `Exceeded allowed rows written in Durable Objects free tier.`，同时登录 RPC 失败，客户端显示「服务器暂时不可用」。Cloudflare 免费数据库写入额度耗尽，影响后台同步和 X 任务，部署前端本身不能恢复额度。
- `addDidFinishTransactionListener` 连没有数据变化的事务也会触发。X 状态镜像每轮都会开启事务，因此旧代码会反复安排两秒后的 alarm。对象重建时恢复数据也触发调度，而 TinyBase 初始化自动保存会重写载入的存储，进一步增加 SQL 写入。
- 改为仅监听帖子、回复的实际变化和 X 的 retry/dismiss 命令；恢复数据库、回传投递结果和刷新统计不触发新任务。alarm 根据各集成真正的下次执行时间继续运行。
- 调度只合并正在执行的存储操作，完成后清除 Promise。每次后续编辑和重连都会重新核对持久化 alarm，修复旧布尔标记阻止丢失 alarm 恢复的问题。
- 加入后台任务开始、完成及状态计数日志，不记录帖子正文或凭据。
- 使用真实 TinyBase Store、SQLite persister 和 X ledger 重现：空任务再次调度、载入即调度、丢失 alarm 无法恢复等 5 项回归用例在旧代码下失败，修复后全部通过。全部 16 个文件、87 项测试通过，类型检查、lint、diff 检查通过。
- 不更改 Cloudflare 付费套餐，不新建真实测试帖子；本次帖子是否最终发出，需要生产投递结果确认。
