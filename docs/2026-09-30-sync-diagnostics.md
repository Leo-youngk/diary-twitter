## 本次修复范围

用户明确要求修复 Buffer → X 投递，症状是「X 1 条正在发」长时间不变。关联范围包括设备间连接恢复，以及 X 状态在设置页中的说明。沿用 TinyBase、Cloudflare Durable Objects 和 Buffer，不迁移服务，不发送测试内容到真实 X 账号。

定位到的缺陷：

- `sending` 缺少下一次唤醒时间，执行中断后可能一直等待。
- 已被 Buffer 接收的任务会因任意数据变化反复查询；查询失败没有提示，限流时也没有尊重 `Retry-After`。
- HTTP 200 内的 GraphQL 权限错误被当成不确定的网络结果。
- 手动重试有 Buffer ID 的任务时，未先核对已有结果，可能重复发布。
- TinyBase 在部分请求错误后仍会让 `load()` 完成；原连接代码只记录错误，随后仍显示已连接。短暂切回前台也未检查无响应的连接。

修复后，已知投递 ID 先查结果再重试；查询逐步退避，遵守限流时间；中断且无法确认的投递显示真实的不确定状态，由用户到 Buffer / X 核实。连接请求失败会断开重连，返回前台立即检查，前台每 30 秒核对一次响应。

## 验收与证据

- Buffer 传输测试覆盖 GraphQL 拒绝、限流等待、网络结果不确定和引用帖文本。
- X 流程测试使用内存 SQLite，覆盖查询节流、中断恢复、已有投递去重、状态核对和限流期间停止后续发送。
- 连接测试覆盖请求失败不误报已连接、返回前台检查、无响应连接恢复。
- 完整 Vitest：10 个测试文件，56 项通过；类型检查和 lint 通过。
- 实际启动 Vite + 本地 Cloudflare Worker，两个独立浏览器数据空间使用同一测试同步码，视口为 390×844 和 1440×1000：通过 UI 发帖后另一端约 884ms 收到；收藏状态互通；断网写入恢复后约 189ms 补齐，两端均 2 条帖子、1 条收藏、0 条 X 投递。这些是本地测量，不代表线上或真机速度。
- 设置页在两个视口查看：待发送任务显示正文和原因，中断任务显示核实提示及重试按钮，无横向溢出。断网测试期间仅出现 favicon / icon 的网络错误；原有键盘代理输入的 aria-hidden 警告与本次改动无关。
- 只读查询真实 Buffer 频道的最近 11 条投递，均为 `sent`。这不能证明用户当前卡住的那条已发出，也不能据此删除或重发它。
